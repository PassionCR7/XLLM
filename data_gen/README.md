# data_gen —— 杭州「周末去哪玩」语料采集

给 `dataset/pretrain_t2t*.jsonl` 补充本地生活类中文语料。产出的 `{"text": ...}`
与现有预训练文件**完全同构**，可直接被 `dataset/lm_dataset.py` 读取。

## 快速开始

```bash
cd <项目根目录>          # 即 data_gen 的上一级

# 看有哪些数据源
python -m data_gen.cli list

# 采集默认源（约 5~8 分钟）
python -m data_gen.cli crawl --max-docs 30

# 采集 + 构建语料，一步到位
python -m data_gen.cli all --max-docs 30

# 用 LLM 把原文改写成第一人称「打卡帖」，合并进语料
python -m data_gen.cli post

# 从打卡帖明细重建语料（默认保留原文，只做去重合并）
python -m data_gen.cli rebuild

# 只看构建结果统计
python -m data_gen.cli stats
```

产出：

```
data_gen/out/
├── raw/                      原始文档（含 url，可复查来源）
│   ├── hangzhou_travel.jsonl
│   └── ...
├── postings/postings.jsonl   LLM 改写出的打卡帖明细（含 origin_title 溯源）
├── corpus/corpus.jsonl       <- 直接喂给训练脚本
└── state.json                断点续爬记录
```

语料里同时存在两种文体，这是**有意为之**：

- **通稿体**（客观叙述）：「11月11日，由西湖岳庙管理处打造的活动正式开启……」

模型能从前者学事实陈述的结构，从后者学口语化的体验表达。早期版本曾让打卡帖
**替换**掉原文，语料从 21,828 字掉到 7,294 字——那是缩水不是补充，已修正。

## 前情：为什么不用 requests / BeautifulSoup

本机 `pip` 源不可达（`No matching distribution found`），`.venv` 也已损坏
（`ModuleNotFoundError: No module named 'encodings'`）。因此**全部代码只用
Python 标准库**：`urllib` 抓取、`html.parser` 解析、`re` 清洗。

想加依赖时先修好虚拟环境：

```bash
rm -rf .venv && uv sync
```

## 架构

```
fetch.py          HTTP 层：编码探测、指数退避重试、按域名限速、robots 检查
extract.py        正文提取：自建轻量 DOM + 文本块密度打分（不依赖固定选择器）
sources.py        站点配置 + 主题词表
crawl.py          编排：发现 -> 抓取 -> 提取 -> 主题过滤 -> 落盘
llm.py            OpenAI 兼容客户端（读 ~/.workbuddy/models.json）
posting.py        把通稿改写成第一人称打卡帖 + 事实核查 + 重合度检查
build_corpus.py   去重（SimHash）+ 重组 + 二次清洗 -> corpus.jsonl
cli.py            命令行
test_data_gen.py  回归测试（16 组，覆盖实测踩过的坑）
```

## 打卡帖改写（调用 LLM）

`post` 命令读 `out/raw/*.jsonl` 的原文，逐篇交给 LLM 改写成第一人称体验帖，
写入 `out/postings/postings.jsonl`，再合并进语料。

```bash
python -m data_gen.cli post                 # 断点续跑，跳过已完成的 url
python -m data_gen.cli post --force          # 全部重跑
```

凭证从 `~/.workbuddy/models.json` 读（`os.path.expanduser`，别写死 `~`——
Git Bash 的 `~` 和 Python 的 `~` 不是同一个路径）。任何 OpenAI 兼容的
`/chat/completions` 端点都能接。

### 密钥安全（三条硬规矩）

`llm.py` 里**没有任何明文密钥**，key 只存在于仓库外的 `~/.workbuddy/models.json`。
但「不硬编码」只是第一层，实测还有两个泄露路径，都已堵上：

**1. `repr` 会把 key 打出来。** `LLMClient` 是 dataclass，默认所有字段进
`__repr__`，于是 `print(client)` 或 traceback 里的局部变量展示就是
`api_key='sk-xxx'`。`_cfg`/`_key` 加了 `repr=False` 不够——`api_key` 是构造
入参，必须单独排除。现在 `repr(client)` 里没有 key。

**2. 错误信息会带出 key。** `chat()` 把 `HTTPError` 响应体拼进 `LLMError`，
而 CLI 直接 print 到终端。部分网关配置出错时会回显请求头，key 就跟着进了
CI 日志 / 截图 / issue。现在所有异常出口都过 `redact(text, secret)`：精确替换
真实 key，并给 `sk-` 前缀串打码。刻意不用「任意长字母数字串」这种宽泛正则，
那会把 URL 和文件名一起打烂。

**3. 不要用命令行传 key。** DEBUG 别加 `--api-key` 参数——shell 历史会留痕，
`ps` 也看得见。要覆盖配置就在代码里 `LLMClient(api_base=..., api_key=...)`。

`test_no_key_leak` 锁死这些行为，包括「URL / 普通错误 / 长数字串不能被误伤」。

### 三道质量闸门

改写比抓取危险得多：模型会「顺手」补细节。所以每篇都要过三关，任一不过就丢弃。

**1. 事实核查 `fact_ok()`** —— 这是最重要的一道。

模型会编造具体数字。实测：原文只写「沿路有茶室」，改写出来变成「人均八十元」。
假价格进了预训练语料，模型会把它当知识学走。做法是抽取原文里的所有数字
断言（阿拉伯数字 + 中文数字），逐个检查是否在改写稿里保留。

两个方向都踩过坑：

- **漏检**：只认阿拉伯数字，`八十元`、`三场` 全部视而不见。补了 `CN_NUM_RE`
  匹配 `[零一二三四五六七八九十百千万两半几]{1,6}(元|块|分钟|小时|公里|米|天|岁)`。
- **误杀**：把 `个/家/人/位` 也当单位，导致「一个人去」「三场大集」被判编造，
  9/20 篇正常稿件被拒。修法：单位只保留金额/时长/距离/年龄；「一」「半」「两」
  单独出现一律视为模糊量；`十几家`、`百余米` 这类带「几/余/多」的跳过不查。

**2. 重合度 `overlap_ratio()`** —— 防止模型直接抄原文。逐字比对 12-gram，
超过 `max_overlap=0.55` 就认为没改到位，丢弃重来。

**3. 可游性标签** —— 提示词要求模型对「不可游玩」的内容（纯政策通报、纯科普
养生）返回 `usable: false`，这条直接跳过。

### 断点续跑

`out/postings/done_urls.json` 记录已完成的 URL。一次跑 25 篇约需 3~5 分钟，
中途失败不用从头来。

### 两个 LLM 使用细节

- **`max_tokens` 要给够（2048 以上）**。当前模型是 reasoning 型，会先消耗
  `reasoning_tokens` 再产出正文。设成 20 时返回空字符串——不是接口坏了，
  是预算被思考吃光了。
- **`--force` 重跑会produce 重复**。同一原文改写两次，语料里就出现两个版本。
  `rebuild_from_postings()` 按 `origin_title` 只留最新一条（实测 39 条 -> 25 条）。

### 三个必须知道的实现细节（都是实测踩出来的）

**1. 编码探测是数据质量的第一道关。** 杭州网主站 `hznews` 是 UTF-8，但
`19lou` 等老站是 GBK。探测顺序：响应头 `charset` → HTML `meta` → 回退
`gb18030`。直接用 UTF-8 解 GBK 会产出满屏乱码却"看起来抓成功了"。

**2. 脏 HTML 会吃掉整页正文。** 实测 `jrsh` 页面存在未闭合的 `<form>` 和
`<input>`。若用 skip 计数器，遇到缺失的结束标签后会永久卡在"跳过中"状态，
把整页正文丢光（表现为 `cjk=0`）。修法两条：
- `input`/`textarea` 等空元素移出 skip 逻辑（它们常被写成未闭合形式）
- 遇到 `div`/`article` 等结构性容器时，清空挂起的 skip 栈

**3. 页脚备案信息会被密度打分误收。** 杭州网系文章末尾稳定出现
「增值电信业务经营许可证：浙B2-...」，长度够、链接少，密度打分认它是正文。
`build_corpus.FOOTER_RE` 里按关键词行级剔除。

### 主题过滤：只看「标题 + 导语前 80 字」

```
必须项（本地性）：标题或导语前 80 字出现杭州地名   -> 否则判 0
意图项（主题性）：同一窗口内出现游玩意图词，或具体游玩对象词
泛词：「公园/景点/路线」只能加成，不能顶替意图项
```

为什么窗口要收到 80 字：曾收录到「冬日温婉水墨扬州」「玩转赣州」两篇，
它们正文某处顺带提到「杭州」，用「标题+正文前 200 字」就漏过去了。本地
游玩内容的导语开头必定交代地点，收到 80 字即可分开。

另一个坑是**歧义地名**：`CITY_TERMS` 里原本有「宋城」，而赣州自称
「江南宋城」，直接误命中。这类词必须移除，只留专指杭州的地名。

`python -m data_gen.test_data_gen` 里有 16 组回归用例，把上述坑都固化了，
改代码后先跑它。

## 隐私与合规

输入是公开新闻稿，人名本来就登在报上。但**把新闻喂进预训练语料是另一回事**：
模型会把「真实姓名 + 真实职务 + 具体言论」记成可复现的知识，生成时凭空造一句
真人说过的话。所以入库前统一脱敏（`build_corpus.scrub_pii`），在三个出口都过一遍：
`build()`、`rebuild_from_postings()`、`Posting.as_corpus_text()`。

处理规则：

| 类型 | 处理 | 理由 |
|---|---|---|
| 记者/通讯员/作者署名 | 整行删除 | 对语言建模零价值 |
| 职务 + 全名（`副书记陈骏辰说`） | 删姓名，留职务（`副书记说`） | 职务有语义，姓名没有 |
| 手机号 / 身份证号 | 替换为 `【电话已脱敏】` | 绝对不进语料 |
| `陈先生`/`李女士` | **保留** | 只给姓是新闻匿名惯例，不构成可识别信息 |

实测效果：重建后 44 篇里，署名、职务+姓名、11 位手机号、18 位身份证号**均为 0 处**，
总字数从 29,122 降到 29,044（少 78 字，就是删掉的那些名字）。回归测试
`test_pii_scrubbed` 和 `test_scrub_idempotent` 锁死这些行为，包括
「负责人介绍」这类不能误伤的边界。

**必须先从 raw 重建，再合并打卡帖。** 直接拿现有 `corpus.jsonl` 当输入会二次污染：
姓名池只能从**原始**文本收集，从已脱敏文本收不到，结果就是「经营者顾大姐」
变成「经营者他，客人都称她顾妈」（他/她混用）。`cli.py rebuild` 已固化为两步：
先 `build(raw)` 生成干净底稿，再 `rebuild_from_postings()` 合并。

**不要试图用正则抓裸姓名。** 试过「百家姓 + 2~3 字 + 是/说」，误伤率极高：
「服务人员是」「武林广场是」「茶山是龙井」「花园里种了桂花」全被命中，语料
会被改成残句。漏网的少数几个靠 `MANUAL_NAMES` 人工补，每轮采集后跑一次扫描
脚本核对即可。宁可漏，不要打烂句子。

**产出目录整体不入库**：`.gitignore` 里写的是 `data_gen/out/`，不是逐个文件。
早期只忽略了 `raw/`、`corpus/`、`state.json`，漏了 `postings/`——而它恰恰是
带人名最全的一份（含 `origin_title` 原文标题）。往公开仓库推等于替别人扩散个人信息。

另外，语料里出现「公园年卡咨询电话 87065409」这类**机构服务电话**，属于公开
服务信息，不属于个人信息泄露，保留。

## 已知局限

- 语料规模小：单轮全源约 40~60 篇、3 万字级别，只够做**领域微调补充**，
  撑不起从零预训练。
- 打卡帖覆盖面窄：目前 25 篇集中在西溪、满觉陇、龙坞、御街等杭州网报道过的
  点位。小红书/马蜂窝这类真正的用户 UGC 抓不到（见上文数据源表），所以
  「各种游玩」的多样性受限于通稿选题。
- 改写有信息损耗：通稿平均 1,148 字，改写成打卡帖后平均 291 字。模型倾向
  抓 2~3 个亮点展开，长尾信息（其他展项、周边餐饮）会丢。要保长尾就得调
  提示词要求「逐段覆盖」，但那样会像通稿，失去口语感。
- 时间偏移：杭州网源随日期滚动，重跑结果会变。
- 无摘要/问答对：目前只产出纯文本。若要 SFT 数据，需在 `build_corpus.py`
  里加模板生成（把正文首段当 answer、标题当 query）。
- 图片说明残留：`_normalize_body` 已过滤大部分「xxx 摄」短行，但长图注仍可能
  混入，量少可接受。
